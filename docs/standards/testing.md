# 测试规范

> 本文件定义项目的测试要求和标准，确保测试质量可控。

---

## 1. 测试原则

- 每个 change 必须包含对应的测试用例
- 测试必须覆盖正常路径和关键异常路径
- 未覆盖的测试场景必须显式说明原因

---

## 2. 测试分层

### 单元测试
- **范围**：Service 层核心业务逻辑
- **框架**：JUnit 5 + Mockito
- **要求**：
  - 覆盖正常路径（happy path）
  - 覆盖关键异常路径（参数为空、数据不存在、权限不足等）
  - 覆盖边界场景（空集合、最大值、最小值等）
  - 每个测试方法必须有明确的断言

### 集成测试
- **范围**：Controller 层接口、跨模块调用
- **要求**：
  - 验证接口入参和出参
  - 验证异常状态码返回
  - 验证事务边界

---

## 3. 测试命名规范

```
测试方法名：should_[预期行为]_when_[条件]
示例：should_returnUser_when_idExists
      should_throwException_when_idIsNull
```

---

## 4. 测试覆盖要求

| 层级 | 最低覆盖率 | 说明 |
|------|-----------|------|
| Service 层 | 80% | 核心业务逻辑必须充分覆盖 |
| Controller 层 | 60% | 接口入参出参验证 |
| DAO 层 | 视情况 | 复杂 SQL 需要测试 |

---

## 5. 评审摘要中的测试说明

每次 `/prepare-review` 生成的评审摘要中，必须包含：

- 本次变更跑了哪些测试
- 哪些场景没有测
- 为什么当前可以接受这些未覆盖的场景

---

## 6. 禁止事项

- 禁止只有 happy path 的测试
- 禁止没有断言的测试
- 禁止测试之间互相依赖执行顺序
