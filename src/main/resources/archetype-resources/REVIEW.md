# REVIEW.md — 评审标准与规范

> 本文件定义代码评审的标准和规范，供 `/prepare-review`、`@reviewer` 子代理及人工评审使用。

---

## 1. 评审目标

- 确保代码实现与 OpenSpec change 工件（proposal / design / tasks）一致
- 发现潜在的架构违规、SQL 风险、逻辑缺陷
- 保证代码质量达到团队可接受标准

---

## 2. 评审检查清单

### 2.1 需求对齐

- [ ] 实现是否覆盖了 tasks.md 中所有任务节点
- [ ] 是否存在超出 change 范围的改动
- [ ] 是否遵循了 design.md 中的技术方案

### 2.2 架构分层

- [ ] Controller 层是否只负责接收请求和返回响应，不包含业务逻辑
- [ ] Service 层职责是否单一，是否存在"过胖"的 Service
- [ ] DAO/Repository 层是否只负责数据访问，不包含业务逻辑
- [ ] 是否存在跨层调用（如 Controller 直接调用 DAO）

### 2.3 代码质量

- [ ] 异常处理是否完整，是否有裸 catch 或吞掉异常的情况
- [ ] 方法长度是否合理（建议不超过 50 行）
- [ ] 命名是否清晰、符合项目约定
- [ ] 是否存在重复代码
- [ ] 注释是否充分，复杂逻辑是否有说明

### 2.4 数据安全

- [ ] SQL 是否有注入风险
- [ ] 批量更新/删除是否有 WHERE 条件限制
- [ ] 是否涉及全表扫描，是否需要索引优化
- [ ] 敏感数据是否有脱敏处理

### 2.5 测试覆盖

- [ ] 是否覆盖了正常路径（happy path）
- [ ] 是否覆盖了关键异常路径和边界场景
- [ ] 测试用例是否有明确的断言
- [ ] 未覆盖的测试场景是否已显式说明原因

### 2.6 隐性约定

- [ ] 是否遵循了 `docs/architecture/implicit-contracts.md` 中的所有约定
- [ ] 是否影响了前端依赖的字段语义
- [ ] 是否破坏了历史兼容性

---

## 3. 评审输出格式

评审结果应包含以下部分：

```markdown
## 评审摘要

### 变更概述
- 本次变更的核心目的
- 涉及的文件和模块

### 发现的问题
| 序号 | 严重程度 | 文件 | 问题描述 | 建议修复方式 |
|------|----------|------|----------|-------------|
| 1    | 高/中/低 | ...  | ...      | ...         |

### 测试覆盖情况
- 已覆盖场景：...
- 未覆盖场景：...
- 原因说明：...

### 隐性约定检查
- 是否涉及隐性约定：是/否
- 涉及内容：...

### 评审结论
- [ ] 通过 — 可以合并
- [ ] 有条件通过 — 修复上述问题后可合并
- [ ] 不通过 — 需要重新设计或实现
```

---

## 4. 严重程度定义

| 等级 | 定义 | 示例 |
|------|------|------|
| **高** | 必须修复，存在线上风险 | SQL 无 WHERE 条件、配置文件误改、数据安全风险 |
| **中** | 建议修复，影响代码质量 | Controller 写业务逻辑、异常处理不完整 |
| **低** | 可选优化，提升可维护性 | 命名不够清晰、缺少注释 |
