# SQL Risk Review — 数据层与 SQL 风险审查

## 职责

**只负责检查数据层风险**，包括 SQL 语句安全性、批量操作风险、索引问题等。

本 skill 不检查架构分层（由 `/java-architecture-review` 负责），不做通用代码评审。

---

## 检查规则

### 规则 1：批量 UPDATE 必须有 WHERE

**红线规则：任何 UPDATE 语句必须有 WHERE 条件，且 WHERE 条件不能为空。**

检查范围：
- `*.xml` 中的 `<update>` 标签
- `@Update` 注解中的 SQL
- Service 中通过 QueryWrapper/LambdaWrapper 构建的更新操作
- 任何动态拼接的 UPDATE 语句

**检查要点：**
- WHERE 子句是否存在
- WHERE 条件是否可能为空（如 `<if test="xxx != null">` 包裹的 WHERE）
- 动态条件是否可能导致全表更新

### 规则 2：批量 DELETE 必须有 WHERE

**红线规则：任何 DELETE 语句必须有 WHERE 条件。**

检查要点同规则 1。

### 规则 3：禁止全表操作

以下操作**直接拦截**：
- `UPDATE table SET ...`（无 WHERE）
- `DELETE FROM table`（无 WHERE）
- `TRUNCATE TABLE`
- `DROP TABLE`（除非在 change 流程中且经人工审批）

### 规则 4：SQL 注入风险

检查是否存在字符串拼接 SQL：
- `"SELECT * FROM user WHERE id = " + id`（禁止）
- 应使用参数化查询：`#{id}` 或 `?` 占位符

### 规则 5：索引使用检查

对于新增或修改的查询：
- 是否使用了索引列
- 是否存在 `SELECT *`（应明确指定字段）
- 是否在索引列上使用了函数
- LIKE 查询是否以 `%` 开头

### 规则 6：事务边界检查

- 批量操作是否在事务内
- 事务范围是否合理（不要过大）
- 异常时是否正确回滚

## 执行步骤

### Step 1：识别数据层变更

扫描以下类型的变更文件：
- `*Mapper.xml` — MyBatis Mapper 文件
- `*Mapper.java` / `*Repository.java` — 数据访问接口
- `*Service.java` — 可能包含数据操作的 Service
- `*.sql` — SQL 脚本文件

### Step 2：读取数据库规范

读取 `docs/standards/database.md` 确认项目数据库规范。

### Step 3：逐文件检查

按上述 6 条规则逐一检查每个数据层变更文件。

### Step 4：输出检查报告

```markdown
## SQL 风险审查报告

### 检查范围
- 检查文件数：[N]
- 涉及数据操作：[查询/更新/删除/DDL]

### 发现的问题
| 序号 | 严重程度 | 文件 | 风险类型 | 问题描述 | 建议修复 |
|------|----------|------|----------|----------|----------|
| 1    | 高/中/低 | ...  | ...      | ...      | ...      |

### 风险统计
| 风险类型 | 数量 | 最高严重程度 |
|----------|------|-------------|
| 批量操作无 WHERE | ... | ... |
| SQL 注入风险 | ... | ... |
| 索引问题 | ... | ... |
| 事务问题 | ... | ... |

### 高风险操作清单
- [ ] [需要人工审批的操作]

### 总结
[整体风险评估和建议]
```

---

## 严重程度定义

| 等级 | 定义 | 示例 |
|------|------|------|
| **高** | 必须修复，存在数据事故风险 | UPDATE 无 WHERE、TRUNCATE、SQL 注入 |
| **中** | 建议修复，存在性能或规范风险 | SELECT *、缺少索引、事务过大 |
| **低** | 可选优化 | 命名不规范、注释不足 |

---

## 注意事项

- 发现**高风险**问题时，必须在报告开头用醒目方式标注
- 涉及受保护的数据库脚本文件时，检查是否经过了 change 流程
- 动态 SQL 要特别关注 `<if>`、`<where>`、`<foreach>` 标签的组合是否可能产生空 WHERE
